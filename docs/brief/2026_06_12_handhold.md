# Product Brief: Codethrough

## Problem

With the increased adoption of AI coding tools, developers are outputting more
code than ever before. Consequently, the bottleneck has shifted from writing
code to reviewing and maintaining it.

Developers are being overwhelmed and getting fatigued by the sheer volume of
code they need to review. This either leads to rushed reviews, or ignored PRs.

Most time consuming parts of code review are:
1. Understanding the problem, the status quo, and other necessary context
2. Understanding how the PR solves the problem, and what the key decisions are
3. Understanding in what order to review the code, and what to focus on

## Target Audience

- **Target profile:** Software engineers at fast-moving companies who are
  experiencing review bottlenecks due to high PR volume.
- **Current workaround:** Sync meetings, written summaries, manually spending
  hours trying to understand everything.

## Core Value Proposition

- Summarizes the problem and the status quo before you start reviewing.
- Explains how the PR solves the problem and what the key decisions are.
- Walks you through the code in the right order while explaining the important
  parts.
- Answers your follow-up questions in real time as you follow the walkthrough.

## Engagement Pattern

- **Trigger:** Developer is assigned to review a PR.
- **Expected frequency:** Up to multiple times a day for active reviewers.

## Monetization Hypothesis

- **Who would pay:** Companies who are spending too much engineering time on
  code reviews, and looking to optimize that process.
- **Why would they pay:** Increase PR merge velocity, and improve overall
  engineer productivity.
- **Pricing guess:** $10-30/seat/month.

## Differentiation

- **Alternative(s):** AI code review assistants (e.g. Greptile, CodeRabbit,
  Copilot), manual reviews, and manual LLM-based workflows.
- **Why the alternatives fall short:** While existing AI code review assistants
  are great at finding problems; serious teams still review code manually to
  understand the proposed solution and drive the key decisions.
- **Why this wins:** Codethrough puts the engineer at the center while holding
  their hand through the whole process to reduce the cognitive burden.

## Validation / Feasibility Test (pre-MVP)

- **Method:** Build a thin throwaway script. It takes a real PR diff as input,
  calls an LLM to generate (1) a summary of the problem, status quo, and key
  decisions, and (2) an ordered, snippet-by-snippet walkthrough with
  explanations, then renders it as a plain local HTML. Run it on 10+ real PRs
  that 5+ target reviewers are actually assigned to, and collect structured
  feedback after each review.
- **Success criteria:**
    - **Quality:** On >=75% of PRs, the reviewer agrees the walkthrough surfaced
      the right snippets, in a sensible order, with accurate explanations.
    - **Value:** >=70% of reviewers report the walkthrough reduced the effort to
      understand the PR.
    - **Demand:** >=60% say they would use it on their next review.
- **Failure criteria:**
    - On a majority of PRs, the walkthrough misses key snippets, mis-orders, or
      contains material inaccuracies (quality below ~50%).
    - Reviewers report no meaningful reduction in effort, or would not change
      their current review workflow.

## MVP Scope

1. Github integration.
    - **Reason:** The most commonly used code hosting platform. Engineers don't
      like switching contexts, so we should integrate where they already are.
2. Summarization of the problem, status quo, and key decisions.
    - **Reason:** Crucial for reducing the cognitive load of the engineers.
3. Guided code walkthrough with snippet-by-snippet navigation.
    - **Reason:** This is the core value prop that differentiates us from
      alternatives. The agent surfaces the important snippets one at a time in
      the right order; the reviewer moves back and forward at their own pace.

## MVP Out of Scope

1. Support for other code hosting platforms like Gitlab and Bitbucket.
    - **Reason:** We want to validate the core value prop before investing in
      less common platforms.
2. Follow-up questions and conversations.
    - **Reason:** Validate that the guided walkthrough alone reduces review
      burden before adding conversational depth.
3. Posting comments back to the PR.
    - **Reason:** Requires GitHub write access. Leaving comments is not a pain
      point.
4. Voice interaction.
    - **Reason:** Higher effort and cost. A text-and-visual walkthrough is
      enough to test the core hypothesis.

## MVP Success Criteria

**Headline metric:** Repeat usage. If reviewers keep reaching for Codethrough on
new PRs, the value is real.

- **Adoption:** >=50% of reviewers given access start a walkthrough in week 1.
- **Repeat usage (headline):** >=40% of activated reviewers use Codethrough on
  the majority (>=50%) of the PRs they are assigned, over a rolling 4-week
  window.
- **Engagement:** >=60% of started walkthroughs are completed (reviewer reaches
  the final snippet).
- **Retention:** >=50% of week-1 users are still starting walkthroughs in
  week 4.
- **Perceived value:** median self-reported review-effort reduction of >=30%.

## 14-day Action Plan

1. **Core walkthrough engine (Days 1-3).** A throwaway script: given a PR diff,
   the LLM returns a summary plus an ordered list of snippets (file, line range,
   explanation, order), rendered as a plain local page.
    - **Testable result:** run it on a real PR and read a coherent, ordered
      walkthrough.
2. **Validation + quality loop (Days 3-5).** Run the engine on 10+ real PRs with
   5+ target reviewers; collect feedback; iterate the prompt until the quality
   bar is hit.
    - **Testable result:** validation success criteria met. Gate: if it fails,
      stop or pivot here.
3. **GitHub ingestion (Days 6-8).** Given a PR URL, fetch the diff and metadata
   (title, description, linked issues) via the GitHub API and feed the engine.
    - **Testable result:** paste a PR URL and get a walkthrough, no manual
      copying.
4. **Web app + reviewer UI (Days 9-12).** Standalone web app: enter a PR URL,
   see the rendered diff with the current snippet highlighted, an explanation
   panel, the summary up top, and back/forward navigation through the snippets.
    - **Testable result:** a reviewer goes end-to-end through a real PR in the
      browser.
5. **Dogfood + instrument (Days 13-14).** Add GitHub OAuth (read private PRs),
   deploy, give 3-5 reviewers access, and instrument the success metrics.
    - **Testable result:** external reviewers use it on their own real PRs;
      metrics are flowing.
